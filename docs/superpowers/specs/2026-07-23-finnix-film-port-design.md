# Finnix Film: Prototype → Production Port — Design

Date: 2026-07-23
Status: Approved (pending final spec review)

## 1. Background

`reference/v0.4/finnix-film.html` is an AI-generated, single-file prototype (React 18 +
Babel-standalone + Tailwind CDN + Chart.js + SheetJS, no build step) for "Finnix Film," a
Thai car window-film/wrap/audio-installation shop chain with branches in Chiang Mai (cm),
Lamphun (lp), Phayao (py), Lampang (lpg), plus a "Central Audio" location (ca). It has no
backend: all data is seeded JS constants living only in React state, lost on every refresh,
and login is email-only with no real authentication. `README-deploy.md` (in the same
folder) confirms this and calls out the need for a real backend before production use.

The client will keep sending new versions of this same single-file prototype in the future
(this one is versioned `v0.4`; expect `v0.5`, `v0.6`, ...), always as a complete replacement
file, generated by whatever AI tool they use — not a diff or changelog.

## 2. Goal

Port the prototype into a real, deployed application:
- **Same or better** visual design and **unchanged functionality** (bugs and visual/UX
  rough edges may be fixed or improved; business functionality must not change).
- Deployed on **Vercel**, backed by **Supabase** (Postgres + Auth + RLS), on a custom
  **domain registered at Cloudflare**.
- All 6 modules (Job Tickets, Wholesale, Stock, Commission, Accounting, Permissions) plus
  Dashboard, ported together in one release — not phased.
- A durable process for absorbing each future prototype drop without re-porting the whole
  app from scratch or clobbering production-only work (real auth, RLS, migrations).

## 3. Non-goals

- Changing business functionality/behavior from what the prototype defines (this port is a
  faithful re-implementation with a real backend, not a redesign of the business logic).
- Building the update-resync process as a fully automated/deterministic tool. Per the
  decision below, it's an AI-assisted (Claude Code) runbook, not a script that runs
  unattended.
- Multi-tenant/multi-client SaaS architecture — this is one company, one Supabase project.

## 4. Architecture

```
Cloudflare (registrar + DNS)  →  Vercel (Next.js App Router)  →  Supabase (Postgres + Auth + RLS)
                                                                   reference/v0.x/*.html
                                                                   (source-of-truth prototype
                                                                    drops — never deployed)
```

- **Frontend/backend:** Next.js (App Router) on Vercel. Server Components for data-heavy
  reads (dashboard, list views); Client Components for interactive forms (ticket/order
  editing, managed dropdowns/chip pickers) — mirrors the prototype's existing
  `useState`-heavy form logic, just backed by Supabase instead of in-memory seeds.
- **Database/auth:** one Supabase project for production data, plus a separate **staging**
  Supabase project (seeded with the prototype's Thai sample data) that local dev and Vercel
  Preview deployments point at — so preview builds/PRs can never touch real shop data.
  Supabase Auth (email + password) replaces the prototype's fake email-only login.
- **Styling:** the prototype's existing CSS custom properties (`--primary`, `--paper`,
  `--ink`, light/dark via `data-theme`, Plus Jakarta Sans + Noto Sans Thai fonts, Font
  Awesome icons) port into a real Tailwind config + `globals.css` — same visual result,
  built at compile time instead of via CDN. The `@media print` job-sheet layout (used to
  print physical work orders for technicians) must keep working exactly as today.
- **Charts:** `DoughnutChart`/`BarChart`/`LineChart` become thin `react-chartjs-2` wrappers
  with equivalent props/behavior. **Excel export:** `xlsx` (SheetJS) stays, same usage.
- **Domain:** register at Cloudflare, add as a custom domain in the Vercel project, DNS
  record set to **DNS-only (grey cloud)** — Cloudflare's proxy in front of Vercel tends to
  break automatic TLS provisioning and some Vercel edge features. Proxying can be revisited
  later if WAF/caching is wanted; not a day-one requirement.

## 5. Data model

Grouped by domain area (full column-level detail belongs in the actual migration files, not
this doc):

- **Identity & shops:** `shops`, `shop_info`, `roles` (kept a real table — the prototype
  lets admins add roles, not a fixed enum), `users` (linked to `auth.users`),
  `user_shop_access` (join table; a `sees_all_shops` flag replaces the prototype's
  `shopAccess: 'all'` special case).
- **Permissions:** one unified `role_permissions(role_id, permission_type, permission_key,
  allowed)` table covers all three of the prototype's permission layers (`nav`,
  `dashboard_widget`, `module_capability`) — same semantics as
  `DEFAULT_NAV_PERMISSIONS`/`DEFAULT_DASHBOARD_PERMISSIONS`/`DEFAULT_MODULE_PERMISSIONS`,
  less schema surface. New capability keys in a future drop are new rows, not new columns.
- **Job tickets:** `tickets`, `ticket_items`, `ticket_item_positions` (film/wrap position
  breakdowns), `ticket_payments`, `ticket_status_history`, `statuses` (editable
  status/color config), `retail_customers`.
- **Wholesale:** `wholesale_customers`, `orders`, `order_items`, `order_returns`,
  `order_payments`, `order_adjustments`, `ws_statuses`.
- **Stock, commission, accounting:** `stock`, `withdrawals`, `commission_rules` (+
  `commission_rule_teams` join table for the `team` array), `expenses`, `petty_cash`.
- **Shared "managed option lists":** the prototype has ~12 near-identical editable
  chip-picker lists that are genuinely flat strings (booking channels, car types, film/wrap
  positions, extra options, slide types, expense categories, payment methods/sources,
  technicians, service items, product categories, service items). These collapse into
  **one** `option_lists(list_key, value, shop_id nullable, sort_order)` table instead of ~12
  tables — a future drop adding a new dropdown or option becomes a data row, not a
  migration.
- **Structured config tables (kept separate, not folded into `option_lists`):** a few
  "managed list"-looking prototype states are actually structured records, not plain
  strings, and need their own shape: `car_models(model, brand, car_type)` (replaces the
  `carModels` array of `{model, brand, carType}`), `price_matrix(car_type, product, price)`
  and `film_price_matrix(category, product, position, car_type, price)` (replace
  `priceMatrix`/`filmPriceMatrix`, each keyed by a multi-column lookup), and
  `corporate_buyers(name, address, tax_id)` (replaces `corporateBuyers`, effectively a
  lightweight B2B customer record). These are still fully admin-editable data — just not
  collapsible into the single generic table above.

**RLS:** every shop-scoped table has a policy built on two SQL helper functions —
`current_user_shops()` (accessible shop ids, or all if `sees_all_shops`) and
`current_user_can(capability_key)` (checks `role_permissions`) — so access control is
enforced in Postgres, not just hidden in the UI as it is in the prototype today.

## 6. Frontend structure

- **Routing** mirrors the prototype's `view` state directly: `app/dashboard`,
  `app/tickets` (+ `[id]`, `+ new`), `app/wholesale` (+ `[id]`), `app/stock`,
  `app/commission`, `app/accounting`, `app/permissions`, `app/login`.
- **Component naming stays close to the prototype's function names**
  (`TicketDetail`, `WholesaleDetail`, `StockModule`, `PermissionsModule`,
  `ManagedDropdown`, `ManagedChipPicker`, `StatusPill`, `PeriodShopFilter`, `JobCalendar`,
  etc.) — not for its own sake, but because it keeps `PROTOTYPE_MAP.md` (Section 7) trivial
  to maintain and future diffing tractable. Large components (e.g. `TicketDetail`, ~1,150
  lines in the prototype) are split into smaller files along the same seams the prototype
  already uses internally (position pickers, payment section, extras section), not
  restructured arbitrarily.
- All Thai UI copy carries over verbatim — no i18n layer, direct port.

## 7. Update / re-sync workflow

This is the core answer to "how do we handle the client sending new prototype versions
in the future":

1. **Every drop is committed as its own version**: `reference/v0.4/finnix-film.html`
   (current), `reference/v0.5/finnix-film.html` next time, etc. — always the complete file,
   committed on its own so `git diff reference/v0.4/... reference/v0.5/...` gives a real,
   permanent diff of exactly what changed.
2. **`docs/PROTOTYPE_MAP.md`** (to be created alongside the initial port) maps every
   prototype constant/component to its production table/file (e.g. `DEFAULT_STATUSES` →
   `statuses` table; `TicketDetail` → `app/tickets/[id]/`). This is what makes a raw diff
   in the prototype file actionable instead of just "some lines changed."
3. **`docs/UPDATING.md`** (to be created alongside the initial port) is the runbook followed
   on every new drop, in an AI-assisted session (Claude Code + the developer), not an
   unattended script:
   - Commit the new file into `reference/vX.Y/`.
   - Diff it against the previous prototype version.
   - Classify each change: **(a) config-as-data** (new car brand, new expense category, new
     status, new permission key) → an `option_lists`/`statuses`/`role_permissions` row edit,
     often **zero code change**; **(b) schema change** (new field on a ticket/order) → new
     Supabase migration + matching UI field; **(c) logic change** (e.g. a commission
     formula, a total calculation) → update the specific function, located via the map;
     **(d) copy/visual-only** → direct text/style edit.
   - Apply the changes, update `PROTOTYPE_MAP.md` for anything new, smoke-test against the
     new prototype file side by side.
   - Commit with a note of which prototype version it reconciles.
4. Because most of the prototype's moving parts are config-as-data (Section 5), a large
   share of future "new version" changes need **no redeploy at all** — they're data edits an
   admin can make directly in the Permissions/Stock/etc. UI. The runbook is only needed for
   genuinely new fields, new logic, or new modules.
5. **Deferred idea, not part of this build:** once the runbook has been used for real on one
   or two future drops, consider formalizing it into a project-specific Claude Code skill
   (`.claude/skills/sync-prototype/`) so the process is picked up automatically in any future
   session. Deliberately not doing this yet — better to base it on how the process actually
   goes than how it's expected to go.

## 8. Deployment

- Vercel project linked to the git repo; env vars split between Preview and Production
  (`NEXT_PUBLIC_SUPABASE_URL`, anon key public; service-role key server-only, Production
  only).
- Two Supabase projects (production, staging) as described in Section 4.
- Migrations tracked in `supabase/migrations/`, applied via the Supabase CLI/MCP tooling to
  each project, versioned alongside the `reference/vX.Y` prototype drops.
- Domain/DNS as described in Section 4.

## 9. Error handling & testing

- **Business-logic functions** the prototype already keeps pure (`orderTotal`, `orderPaid`,
  `ticketTotal`, `itemNetPrice`, commission calculations, `thaiBahtText`) are ported with
  unit tests — since functionality must stay unchanged, these tests are what prove that on
  every future re-sync.
- **A handful of Playwright smoke tests** for the flows that would actually hurt if broken:
  login, create/pay a ticket, print a job sheet, wholesale price approval, a permissions
  change taking effect. Not full coverage — a fast regression net to run after applying each
  prototype update.
- **RLS policy checks:** scripted checks that, e.g., a `sales` role truly cannot read another
  shop's tickets — since shop/role scoping becomes real security, not just UI hiding.
- **Error handling:** Supabase errors surfaced as inline/toast messages instead of silently
  failing, Next.js error boundaries per route segment, basic form validation before submit
  (the prototype has little today — one of the "fix bugs/improve" areas explicitly okayed
  for this port).

## 10. Key decisions (recap)

| Decision | Choice |
|---|---|
| Update format from client | Always a complete new single-file HTML replacement |
| Framework | Next.js (App Router) |
| Auth | Supabase Auth, email + password |
| Rollout scope | All 6 modules + dashboard in one release |
| Re-sync process | AI-assisted (Claude Code) runbook, not a deterministic script |
| Config vs. code | Prototype's option lists/permissions/statuses become admin-editable data, not hardcoded |
