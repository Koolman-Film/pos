# ออกแบบ: พนักงานขายในโมดูลขายส่ง และการแยกยอดขายปลีก/ขายส่ง

เขียนไว้ก่อนลงมือปิดช่องโหว่โมดูลขายส่ง ตามที่คุยกันไว้สองเรื่อง

1. โมดูลขายส่งมีพนักงานขายสองคน — **โหน่ง** และ **เคน** — ขายภายใต้ชื่อ
   **Finnix North** และต้องแยกดูรายการและยอดขายรายคนได้
2. บางสาขา เช่น **Central Audio** ขายทั้งปลีก (ผ่าน Book งาน) และส่ง (ผ่าน
   ขายส่ง) การแสดงยอดขายต้องแยกสองช่องทางนี้ออกจากกัน

---

## สิ่งที่ต้องรู้ก่อน: ตอนนี้ยอดขายส่งไม่ถูกนับที่ไหนเลย

ตรวจโค้ดแล้วพบว่านี่ไม่ใช่เรื่อง "แสดงผลแยกไม่ได้" แต่เป็นเรื่องที่ **ยอดขายส่ง
ไม่ปรากฏในตัวเลขใดของระบบเลย**

| ที่                           | สูตรที่ใช้อยู่                                      | ขายส่งอยู่ในนั้นไหม |
| ----------------------------- | --------------------------------------------------- | ------------------- |
| แดชบอร์ด → ยอดขายรวม          | ใบงานที่ส่งมอบ + ประกันที่ขาย                       | ❌                  |
| แดชบอร์ด → เปรียบเทียบรายสาขา | สูตรเดียวกัน                                        | ❌                  |
| โมดูลรายได้                   | อ่านจาก `tickets` และ `insurance_policies` เท่านั้น | ❌                  |

แปลว่าสำหรับ Central Audio ที่ยอดส่วนใหญ่มาจากขายส่ง ตัวเลขบนแดชบอร์ดวันนี้
**ต่ำกว่าความจริงเกือบทั้งก้อน** — ที่ผ่านมาไม่มีใครสังเกตเพราะข้อมูลตัวอย่างมี
ใบงานเป็นหลัก

การ "แยกแสดงปลีก/ส่ง" จึงไม่ใช่การเพิ่มตัวกรอง แต่คือการ **เอาขายส่งเข้าระบบ
ตัวเลขก่อน แล้วค่อยติดป้ายว่ามาจากช่องทางไหน**

---

## 0. Finnix North ต้องมีตัวตนก่อน

**สร้างแล้วในระบบจริง** (ยืนยัน 10 ก.ย. 2569) ฐานข้อมูลที่ผมใช้พัฒนายังมี 5 สาขา
ผมจะเพิ่ม North เข้าข้อมูลตัวอย่างเอง เพื่อให้ทดสอบเคสขายส่งล้วนได้

สามอย่างที่ต้องตั้งค่าให้ North ตอนสร้าง

1. **ข้อมูลนิติบุคคล** (`shop_info`) — ชื่อ ที่อยู่ เลขผู้เสียภาษี เพราะเอกสารทุกใบ
   ที่ออกจาก PO ของ North จะพิมพ์ชื่อนี้ ตอนนี้ทุกสาขายังว่างอยู่
2. **แหล่งเงิน** — บัญชีธนาคารและยอดตั้งต้นของ North ในโมดูลการจัดการเงิน/บัญชี
   ไม่งั้นเงินที่ North รับมาจะไม่มีที่ลง
3. **สิทธิ์เข้าถึง** — โหน่งกับเคนเห็นเฉพาะ North (ถ้าจะให้มีบัญชีเข้าระบบ)

### เอกสารของขายส่ง — สี่ใบ ไม่มีใบกำกับภาษี

ยืนยันแล้วว่าขายส่งไม่ออกใบกำกับภาษีอยู่แล้ว ออกสี่ใบนี้เท่านั้น

| เอกสาร             | ออกเมื่อ     | มีในระบบแล้วไหม |
| ------------------ | ------------ | --------------- |
| ใบแจ้งหนี้         | ตกลงราคาแล้ว | ✅              |
| **ใบส่งของ**       | ส่งของ       | ❌ **ยังไม่มี** |
| **ใบรับคืนสินค้า** | ลูกค้าคืนของ | ❌ **ยังไม่มี** |
| ใบเสร็จรับเงิน     | รับเงินแล้ว  | ✅              |

### จุดที่ทำให้ทั้งหมดนี้ลงตัว

สองใบที่ขาดไป **คือเหตุการณ์ทางบัญชีสองเหตุการณ์ที่ยังไม่มีที่บันทึกพอดี**

- **ใบส่งของ = วันที่รับรู้รายได้** ออกใบส่งของคือส่งของ และส่งของคือจุดที่นับ
  เป็นยอดขาย (`orders.delivered_at`) ไม่ต้องมีปุ่มแยกให้กดสองที ออกใบส่งของ
  แล้ววันจัดส่งถูกบันทึกทันที
- **ใบรับคืนสินค้า = วันที่ลดยอดขาย** (`order_returns.returned_at`) ตอนนี้
  `order_returns` เก็บได้แค่ว่าคืนอะไรกี่ชิ้น ไม่มีวันที่ จึงกระทบยอดตามเดือน
  ไม่ได้

ทำสองใบนี้ แล้วได้วันที่สองตัวที่ข้อ 2 ทั้งหมดต้องใช้ — เอกสารกับตัวเลขเป็น
เรื่องเดียวกัน ไม่ใช่งานสองก้อน

## 1. พนักงานขาย (โหน่ง / เคน)

### เก็บที่ไหน

`orders.sales_by text not null default ''` — เก็บเป็น **ชื่อ** ไม่ใช่ FK ไป
`app_users`

เหตุผล: โหน่งกับเคนอาจไม่มีบัญชีเข้าระบบ และระบบนี้เก็บ "คน" แบบนี้อยู่แล้วทุกที่ —
`tickets.tech_by_category` เก็บชื่อช่าง, `commission_rule_teams.team_member`
เก็บชื่อทีม, `service_visits.sales_by` เก็บชื่อเซลล์ที่รับรถ ถ้าบังคับให้เป็น FK
จะต้องสร้างบัญชีผู้ใช้ให้คนที่ไม่ต้องใช้ระบบ ซึ่งเป็นการสร้างงานเพื่อให้ตารางสวย

รายชื่อมาจาก option list ใหม่ `sales_people` แก้ได้จากหน้าจอเหมือน `technicians`

`option_lists` รองรับรายการ **แยกรายสาขา** อยู่แล้ว (คอลัมน์ `shop_id`) — โหน่งกับ
เคนจึงอยู่ในรายการของ North เท่านั้น ไม่ไปโผล่ในตัวเลือกของเชียงใหม่หรือลำพูน และ
สาขาอื่นเพิ่มพนักงานขายของตัวเองได้โดยไม่กระทบกัน

เก็บที่ `orders` ไม่ใช่ที่สาขา เพราะแม้วันนี้พนักงานขายจะอยู่ที่ North สาขาเดียว การ
ผูกกับสาขาจะทำให้ PO ของสาขาอื่นระบุคนขายไม่ได้เลย ซึ่งเป็นข้อจำกัดที่ไม่มีเหตุผล
รองรับ

### แสดงตรงไหน

- **ฟอร์ม PO** — ช่อง "พนักงานขาย" ตั้งค่าเริ่มต้นเป็นชื่อผู้ใช้ที่ล็อกอินอยู่
  ถ้าชื่อนั้นอยู่ในรายการ
- **รายการขายส่ง** — ปุ่มกรองรายคน (ทั้งหมด / โหน่ง / เคน / ไม่ระบุ) วางข้างตัวกรอง
  ลูกค้าและสินค้าที่มีอยู่แล้ว
- **สรุปรายคน** — แถบเล็กเหนือรายการ: ยอดขาย, จำนวน PO, ค้างรับ ต่อคน

### ข้อควรระวัง

PO เดิมทั้งหมดไม่มีพนักงานขาย จะขึ้นเป็น **"ไม่ระบุ"** ไม่เดาให้ และไม่ยัดให้คนใด
คนหนึ่ง — ตัวเลขรายคนที่มีของเก่าปนอยู่จะแย่กว่าตัวเลขที่บอกตรงๆ ว่ายังไม่ได้ระบุ

ไม่ผูกกับค่าคอมมิชชั่นในรอบนี้ ถ้าจะคิดคอมจากยอดรายคนค่อยทำเป็นกฎในโมดูล
ค่าคอมมิชชั่นทีหลัง เพราะกฎคอมมีเงื่อนไขของตัวเอง (ขั้นบันได, ทีม, เฉพาะสาขา)

## 2. แยกขายปลีก / ขายส่ง

### หลักการ

เพิ่ม **ช่องทางการขาย (channel)** เป็นมิติหนึ่งของทุกยอดขาย

| ช่องทาง | มาจาก            | นับเมื่อไหร่                   |
| ------- | ---------------- | ------------------------------ |
| ขายปลีก | ใบงานใน Book งาน | วันที่รับงาน (เหมือนเดิม)      |
| ขายปลีก | ประกัน           | วันที่ขายกรมธรรม์ (เหมือนเดิม) |
| ขายส่ง  | PO ในโมดูลขายส่ง | **วันที่จัดส่ง**               |

"ตอนจัดส่ง" เป็นข้อที่คุณเลือกไว้แล้วตอนคุยเรื่องขายส่งรอบก่อน และยังไม่ได้ทำ —
ต้องเพิ่ม `orders.delivered_at` ก่อน ไม่งั้นขายส่งไม่มีวันที่ให้นับเข้าเดือนไหนเลย
**เรื่องนี้เป็นเงื่อนไขของทุกอย่างในหัวข้อนี้**

และเป็นข้อที่ถูกต้องยิ่งขึ้นเมื่อรู้ว่า **ขายส่งส่งของก่อน แล้วค่อยได้เงินทีหลัง**
ถ้านับตอนรับเงิน ยอดขายเดือนนี้จะเป็นของที่ส่งไปเมื่อไหร่ก็ไม่รู้ และเดือนที่ส่งของ
เยอะจะดูเหมือนเดือนที่ไม่ได้ขายอะไรเลย

ผลตามมาที่ต้องรับ: **ยอดขายกับเงินที่เข้าจริงจะไม่เท่ากันเสมอ** ส่วนต่างคือ
ค้างรับ ซึ่งมีที่แสดงอยู่แล้วในการ์ดลูกหนี้และคอลัมน์ค้างรับ/ค้างสุทธิ และการ์ด
เงินอยู่ที่ไหนบ้างจะไม่ขยับจนกว่าเงินจะเข้าจริง — ตรงตามที่ควรเป็น

### แสดงตรงไหน

- **โมดูลรายได้** — เพิ่มคอลัมน์ ช่องทาง และปุ่มกรอง (ทั้งหมด / ปลีก / ส่ง)
  พร้อมยอดรวมแยกสองก้อน PO หนึ่งใบลงเป็นหนึ่งบรรทัดต่อหนึ่งรายการสินค้า
  เหมือนที่ใบงานลงเป็นหนึ่งบรรทัดต่อหนึ่งชนิดสินค้าอยู่แล้ว
- **แดชบอร์ด → ยอดขายรวม** — ตัวเลขใหญ่รวมทั้งสองช่องทาง (เพราะเป็นเงินของร้าน
  ทั้งคู่) และรายละเอียดข้างใต้แยก **ขายปลีก / ขายส่ง** เพิ่มจากที่ตอนนี้แยกตาม
  ชนิดสินค้า
- **เปรียบเทียบรายสาขา** — เพิ่มสองคอลัมน์ ปลีก / ส่ง ข้างยอดขายรวม จะได้เห็นว่า
  Central Audio กับเชียงใหม่ทำเงินคนละแบบ ซึ่งเป็นสิ่งที่การเทียบสาขาแบบเดิม
  มองไม่เห็น

  Finnix North จะขึ้นปลีก 0 ทั้งคอลัมน์ตลอด เพราะเป็นสาขาขายส่งอย่างเดียว —
  ถูกต้องแล้ว ไม่ใช่ข้อมูลหาย

### ข้อควรระวังที่สำคัญที่สุด

**ยอดขายรวมจะกระโดดขึ้นทันทีที่ทำเรื่องนี้เสร็จ** เพราะขายส่งเพิ่งถูกนับเป็นครั้งแรก
ไม่ใช่บั๊ก แต่ต้องรู้ล่วงหน้า ไม่งั้นจะดูเหมือนตัวเลขเพี้ยน โดยเฉพาะถ้าเทียบกับ
เดือนก่อนที่ยังไม่ได้นับ

ผมจะทำให้ **ตัวเลขเดิมยังตรวจสอบย้อนได้** ด้วยการแยกช่องทางไว้ตลอด ไม่ใช่รวมก้อน
เดียวจนแยกไม่ออกว่าส่วนไหนเป็นของใหม่

## 3. การรับเงินขายส่ง — เช็คลงวันที่ล่วงหน้า

ขายส่งส่วนใหญ่รับเป็นเช็คและมักลงวันที่ล่วงหน้า ซึ่งแปลว่า **เหตุการณ์เดียวใน
ระบบวันนี้ จริงๆ แล้วเป็นสามเหตุการณ์**

| #   | เหตุการณ์                        | ใครทำ            | เกิดอะไรขึ้นจริง                |
| --- | -------------------------------- | ---------------- | ------------------------------- |
| 1   | รับเช็คมา                        | sale             | มีกระดาษอยู่ในมือ ยังไม่ใช่เงิน |
| 2   | ถึงวันที่หน้าเช็ค / นำเข้าธนาคาร | แอดมิน           | รอผล                            |
| 3   | เช็คผ่าน หรือ เด้ง               | แอดมิน/ผู้บริหาร | เงินเข้าจริง หรือไม่เข้า        |

`order_payments` วันนี้มีแค่ จำนวน + วิธี + วันที่ จึงบันทึกได้เหตุการณ์เดียว และ
ระบบเลยไม่มีทางแยกได้ว่า "รับเช็คแล้ว" กับ "ได้เงินแล้ว" ต่างกัน

### สิ่งที่ตัดสินใจแล้ว

- **ตัดหนี้เมื่อเช็คผ่านจริง** — ลูกค้ายังค้างอยู่จนกว่าเงินจะเข้า
- **ออกใบเสร็จตอนรับเช็ค** — ตามที่ร้านทำอยู่
- **sale แจ้งได้ แอดมิน/ผู้บริหารยืนยัน** — sale บันทึกว่ารับเช็คมา แต่เงินยังไม่เข้า
  ระบบจนกว่าคนที่มีสิทธิ์จะกดยืนยัน

### ผลที่ตามมา และวิธีรับมือ

สองข้อแรกรวมกันแปลว่า **ใบเสร็จถูกออกไปแล้ว ทั้งที่หนี้ยังไม่ถูกตัด** ซึ่งไม่ใช่
ความขัดแย้ง — เป็นความจริงของธุรกิจที่ระบบต้องรองรับ ไม่ใช่ปัดตก แต่มีผลสองอย่าง
ที่ต้องจัดการ

1. **ใบเสร็จต้องบอกว่ารับเป็นเช็คใบไหน** เลขที่เช็ค ธนาคาร และวันที่หน้าเช็ค
   พิมพ์ลงในใบเสร็จ ใบเสร็จที่เขียนแค่ "รับเงินแล้ว 50,000" ทั้งที่เป็นเช็คลงวันที่
   หน้า เป็นเอกสารที่อ่านแล้วเข้าใจผิดได้ทั้งสองฝ่าย
2. **เช็คเด้งหลังออกใบเสร็จไปแล้ว** ต้องมีทางบันทึก ระบบจะให้ทำเครื่องหมายว่า
   เด้ง พร้อมวันที่และเหตุผล หนี้กลับมาเองอัตโนมัติ และใบเสร็จใบนั้นถูกทำเครื่องหมาย
   ว่ายกเลิก — **ไม่ลบ** เพราะมันออกไปอยู่ในมือลูกค้าแล้ว การลบทิ้งคือการทำลาย
   หลักฐานว่าเคยออก

### โครงสร้าง

`order_payments` เพิ่มฟิลด์เพื่อให้หนึ่งแถวเล่าได้ทั้งสามเหตุการณ์

| ฟิลด์                                     | ความหมาย                                             |
| ----------------------------------------- | ---------------------------------------------------- |
| `status`                                  | `แจ้งแล้ว` → `รับเงินแล้ว` → (`เด้ง` ถ้าเช็คไม่ผ่าน) |
| `cheque_no`, `cheque_bank`, `cheque_date` | ข้อมูลเช็ค ว่างถ้ารับเป็นเงินสด/โอน                  |
| `reported_by`, `reported_at`              | sale คนที่แจ้ง และวันที่แจ้ง                         |
| `cleared_at`, `cleared_by`                | วันที่เงินเข้าจริง และคนที่ยืนยัน                    |
| `bounced_at`, `bounce_note`               | ถ้าเช็คเด้ง                                          |

เงินสดกับเงินโอนใช้เส้นทางเดียวกัน แค่ข้ามขั้น — บันทึกแล้วยืนยันได้ทันที ไม่ต้อง
มีสองระบบให้จำ

### ตัวเลขไหนใช้อะไร

| ตัวเลข             | นับจาก                                          |
| ------------------ | ----------------------------------------------- |
| ยอดขาย             | **วันส่งของ** ไม่เกี่ยวกับการรับเงินเลย (ข้อ 2) |
| ค้างรับ / ตัดหนี้  | เฉพาะ `รับเงินแล้ว`                             |
| เงินอยู่ที่ไหนบ้าง | เฉพาะ `รับเงินแล้ว` ลงวันที่ `cleared_at`       |
| ใบเสร็จรับเงิน     | ออกได้ตั้งแต่ `แจ้งแล้ว` พร้อมข้อมูลเช็ค        |

จุดสำคัญ: **การ์ดเงินอยู่ที่ไหนบ้างจะไม่ขยับเพราะเช็คที่ยังไม่ผ่าน** ซึ่งถูกต้อง —
เช็คในลิ้นชักไม่ใช่เงินในบัญชี

### ของแถมที่ได้มาฟรี

เมื่อเก็บวันที่หน้าเช็คแล้ว ระบบตอบได้ว่า **เดือนหน้าจะมีเงินเข้าเท่าไหร่** — เช็คที่
ถืออยู่ เรียงตามวันที่ลงหน้าเช็ค พร้อมใบที่เลยกำหนดแล้วยังไม่ได้ยืนยัน ซึ่งคือใบที่
ต้องไปตามธนาคาร

### สิทธิ์

คีย์ใหม่ **ขายส่ง: ยืนยันเงินเข้า** ตั้งต้นเปิดให้แอดมินกับผู้บริหาร sale บันทึกและ
แจ้งได้ แต่กดยืนยันไม่ได้ — ตรวจในฐานข้อมูลด้วย trigger ไม่ใช่แค่ซ่อนปุ่ม

### ลำดับ

ทำหลังข้อ 3 (ตัวกรองรายพนักงานขาย) และ **ก่อน** ข้อ 4-5 เพราะข้อ 4-5 คำนวณ
ค้างรับกับเงินเข้า ซึ่งนิยามจะเปลี่ยนไปตามเรื่องนี้

## เรื่องที่ยังค้างจากรอบก่อน (ไม่ได้อยู่ในเอกสารนี้)

ยังมีของที่ตกลงกันไว้แล้วแต่ยังไม่ได้ทำ และควรทำในรอบเดียวกับข้อ 1 เพราะแตะ
ตารางเดียวกัน

- แจ้งให้รู้ว่าเป็นรายได้ที่ยังไม่ได้รับเงิน
- การคืนสินค้าต้องลดยอดขายตามวันที่คืน (`order_returns.returned_at`)
- หนี้สูญที่เก็บไม่ได้ ต้องบันทึกไว้และกระทบยอด — ไม่ลดยอดขาย แต่ลงเป็นค่าใช้จ่าย
  พร้อมเหตุผล วันที่ และผู้อนุมัติ
