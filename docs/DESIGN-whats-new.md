# ออกแบบ: บอกผู้ใช้ว่ามีอะไรเปลี่ยนไปบ้าง

คำขอ: อยากเพิ่มการแนะนำตอนเข้าใช้งานครั้งแรกหลังระบบปรับปรุงใหม่ เหมือนเป็นการทัวร์ระบบ
เพื่อให้ผู้ใช้รู้ว่ามีอะไรเปลี่ยนไปบ้าง

---

## สิ่งที่ต้องรู้ก่อน

- **ระบบเปลี่ยนแทบทุกสัปดาห์** เฉพาะช่วงทดลองใช้มีการแก้ที่ผู้ใช้เห็นผลแล้วอย่างน้อย
  22 เรื่อง (`docs/RELEASE-post-trial-fixes.md` ข้อ 1–22) และ **ยังไม่เคยมีใครบอกพนักงาน
  สักเรื่องเดียว** ทุกคนเจอของใหม่เอาเองตอนกำลังทำงานอยู่ นี่คือปัญหาจริงที่ต้องแก้ก่อน
- **ตอนนี้ไม่มีเลขรุ่นอยู่ที่ไหนเลย** มุมล่างซ้ายเขียน "Prototype v0.4" ตายไว้ในโค้ด
  ไม่ได้ขยับมาหลายเดือน ระบบจึงยังตอบไม่ได้ด้วยซ้ำว่า "ครั้งก่อนคุณเห็นรุ่นไหน"
- **กลไกที่ต้องใช้ มีอยู่แล้วเกือบครบ** — สิทธิ์รายเมนู (`hasNav`) และรายความสามารถ
  (`caps`) สำหรับเลือกว่าใครควรได้ยินเรื่องไหน และตาราง `alert_acknowledgements`
  (migration 0058) เป็นตัวอย่างสำเร็จรูปของการจำ "คนนี้รับทราบแล้ว" ไว้ในฐานข้อมูล
- **เครื่องที่หน้าร้านใช้ร่วมกันหลายคน** การจำว่า "อ่านแล้ว" ไว้ในเบราว์เซอร์จึงใช้ไม่ได้
  คนแรกที่กดปิด จะปิดแทนทุกคนที่มาใช้เครื่องนั้นต่อ — ต้องจำรายคนในฐานข้อมูล
  เหตุผลเดียวกับที่ 0058 ตัดสินใจไว้แล้ว
- **วัตถุดิบมีอยู่แล้ว** ข้อความใน runbook กับใน commit เขียนเป็นภาษาร้านอยู่แล้ว
  ("รายงานขายส่ง บอกเลขที่เช็คและวันที่หน้าเช็ค") ไม่ต้องเริ่มเขียนใหม่จากศูนย์

---

## ความเห็นต่อข้อเสนอ

**ส่วนที่ถูก และคงไว้:** คนต้องรู้ว่าอะไรเปลี่ยน โดยไม่ต้องไปหาเอง และต้องรู้ตอนที่
กลับเข้ามาใช้หลังอัปเดต

**สามจุดที่ขอปรับ:**

### 1. "ทัวร์ระบบ" กับ "มีอะไรใหม่" เป็นคนละเรื่อง — ทำคนละอย่าง

คำขอรวมสองอย่างไว้ด้วยกัน แต่มันตอบคนละคำถามของคนละคน:

|            | คนใหม่วันแรก            | คนเดิมหลังอัปเดต            |
| ---------- | ----------------------- | --------------------------- |
| คำถามในหัว | "ระบบนี้ทำอะไรได้บ้าง"  | "เมื่อวานยังไม่มีอันนี้นี่" |
| ต้องการ    | ลำดับงานที่ตัวเองต้องทำ | **ส่วนต่าง** จากที่เคยรู้   |
| ความถี่    | ครั้งเดียวในชีวิต       | ทุกครั้งที่อัปเดต           |

ถ้าทำเป็นทัวร์เดียว คนใหม่จะได้ฟังรายการเปลี่ยนแปลงของฟีเจอร์ที่ตัวเองยังไม่เคยใช้
ส่วนคนเก่าจะถูกสอนเรื่องที่รู้อยู่แล้ว **ของที่เจ็บตอนนี้คืออย่างที่สอง** เอกสารนี้จึง
เสนอให้ทำ "มีอะไรใหม่" ก่อน แล้วค่อยทำ "เริ่มใช้งาน" สำหรับพนักงานใหม่ทีหลัง

### 2. ไม่เอาป๊อปอัพทีละหน้าแบบกด "ถัดไป"

พนักงานเปิดระบบตอนลูกค้ายืนรออยู่ตรงหน้า หน้าต่างที่มาขวางงานในวินาทีแรก จะถูกกดปิด
โดยไม่อ่าน — แล้วข้อมูลนั้นก็หายไปตลอดกาล คนที่ควรได้ประโยชน์ที่สุดคือคนที่รีบที่สุด
และเป็นคนที่จะไม่มีวันได้อ่าน

และทัวร์แบบชี้ปุ่มสอนได้แค่ "ปุ่มอยู่ตรงนี้" ซึ่งไม่ใช่สิ่งที่ยากในระบบนี้ ของที่ยากคือ
**ความหมายที่เปลี่ยน** เช่น "ตัวกรองสาขาของแท็บรายการสต็อก ไม่กรองตารางประวัติแล้ว"
วงกลมสีรอบปุ่มบอกเรื่องแบบนี้ไม่ได้

### 3. แยกประเภทการเปลี่ยนแปลง แล้วใช้วิธีบอกคนละแบบ

ไม่ใช่ทุกการเปลี่ยนแปลงสมควรได้เสียงดังเท่ากัน:

| ประเภท                        | ตัวอย่างจริงจากที่ทำไปแล้ว                       | วิธีบอก                               |
| ----------------------------- | ------------------------------------------------ | ------------------------------------- |
| **ของใหม่** ที่ไม่เคยมี       | ตัวกรองประวัติสต็อก, พิมพ์ค้นหาสินค้าได้         | ป้าย "ใหม่" ตรงของจริง + อยู่ในรายการ |
| **ของเดิมที่ความหมายเปลี่ยน** | ตัวกรองสาขาของอีกแท็บ ไม่กรองตารางประวัติแล้ว    | คำเตือนในหน้านั้น ค้างไว้สักเดือน     |
| **ของที่แก้ให้ถูก**           | ใบงานติดตั้งแยกตามวันติดตั้ง, เลขที่เช็คในรายงาน | อยู่ในรายการเฉย ๆ ไม่ต้องเด้ง         |
| **ของหลังบ้าน**               | ความเร็ว, จัดระเบียบโค้ด                         | **ไม่ต้องบอก**                        |

แถวสุดท้ายสำคัญที่สุด ถ้าเอาทุก commit มาขึ้นจอ รายการจะยาวจนไม่มีใครอ่าน แล้วเรื่อง
ที่สำคัญจริงจะจมหายไปกับมัน

## ที่เสนอ: สี่ชั้น

### ชั้นที่ 0 · เลขรุ่น (ฐานของทุกอย่าง)

เลขรุ่นที่เดินหน้าทุกครั้งที่ขึ้นระบบ แทน "Prototype v0.4" ที่ตายอยู่ และจำรายคนว่า
**เห็นถึงรุ่นไหนแล้ว** ทั้งหมดที่เหลือในเอกสารนี้คำนวณจากส่วนต่างสองตัวเลขนี้

### ชั้นที่ 1 · หน้า "มีอะไรใหม่" (อยู่ตลอด ไม่มีวันหาย)

- เข้าได้ตลอดเวลาจากเมนูชื่อผู้ใช้มุมขวาบน ไม่ใช่เห็นครั้งเดียวแล้วหาย
- เรียงจากรุ่นล่าสุดลงไป **เห็นเฉพาะเรื่องที่เกี่ยวกับสิทธิ์ของตัวเอง**
- แต่ละเรื่องมีสามบรรทัด: **อะไรเปลี่ยน · ทำไม · ต้องทำอะไรต่อไหม**
  บรรทัดที่สามส่วนใหญ่คือ "ไม่ต้องทำอะไร ใช้ได้เลย" และการได้อ่านประโยคนั้นมีค่า
- มีปุ่มไปที่หน้านั้นเลย (กรองไว้ให้แล้วถ้าทำได้) — หลักเดียวกับทุกบรรทัดในกระดิ่ง

นี่คือชั้นที่ต้องมีก่อนเพื่อน ชั้นอื่นเป็นแค่ทางเดินมาที่นี่

### ชั้นที่ 2 · แถบบาง ๆ ใต้หัวข้อ ตอนเข้าครั้งแรกหลังอัปเดต

```
ระบบอัปเดตแล้ว · มี 3 เรื่องที่เกี่ยวกับงานของคุณ        [ ดูว่าอะไรเปลี่ยน ]  [ ไว้ก่อน ]
```

- **แถบ ไม่ใช่หน้าต่างกลางจอ** — อ่านได้โดยไม่ต้องหยุดงาน และไม่ต้องกดปิดก่อนถึงจะ
  ทำงานต่อได้
- กด **ไว้ก่อน** แล้วหายไปเลย ไม่กลับมากวนพรุ่งนี้ (ต่างจากกติกาของกระดิ่ง เพราะเรื่อง
  ที่ค้างอยู่สมควรถูกเตือนซ้ำ ส่วนข่าวที่อ่านแล้วหรือเลือกจะไม่อ่าน ไม่ใช่เรื่องค้าง)
- แต่ **จุดสีบนเมนูชื่อผู้ใช้ยังอยู่** จนกว่าจะเปิดอ่าน ข้อมูลจึงไม่หายไปไหน แค่ไม่ยืนขวาง
- ขึ้นเฉพาะเมื่อมีเรื่อง **ที่เกี่ยวกับคนนั้น** จริง ๆ คนที่ไม่ได้เข้าขายส่ง ไม่ต้องรู้เรื่อง
  คอลัมน์เลขที่เช็ค

### ชั้นที่ 3 · ป้าย "ใหม่" ตรงของจริง

ป้ายเล็ก ๆ ติดอยู่กับปุ่มหรือช่องที่เพิ่งเพิ่ม บนหน้าจอจริง ไม่ใช่ในป๊อปอัพ

- หายเองเมื่อ **ใช้ของชิ้นนั้นแล้ว** หรือเมื่อครบ 14 วัน
- นี่คือ "ทัวร์" ในเวอร์ชันที่ไม่ขวางทาง — มันไปเจอคนตอนที่คนเปิดหน้านั้นเพื่อจะทำงาน
  นั้นอยู่พอดี ซึ่งเป็นวินาทีเดียวที่คนพร้อมจะสนใจ ไม่ใช่ตอนเพิ่งล็อกอิน

### ชั้นที่ 4 · คำเตือนสำหรับของที่ความหมายเปลี่ยน

ใช้น้อยครั้ง แต่ดังกว่าชั้นอื่น — ข้อความค้างอยู่ในหน้านั้นเองสักเดือนแล้วลบออกจากโค้ด

> ตัวกรองสาขาของแท็บ "รายการสต็อก" ไม่กรองตารางนี้แล้ว — แท็บนี้มีตัวกรองสาขาของตัวเอง

ใช้เฉพาะกับของที่ **คนเคยพึ่งพาแล้วมันเปลี่ยนไปโดยไม่มีอะไรบนจอบอก** ซึ่งเป็นกรณี
เดียวที่คนจะอ่านตัวเลขผิดโดยไม่รู้ตัว ไม่ใช่ทุกการเปลี่ยนแปลงสมควรได้ช่องนี้

## ใครเห็นเรื่องไหน

หลักเดียวกับกระดิ่ง (`docs/DESIGN-notifications.md`): **เห็นเฉพาะเรื่องที่เกี่ยวกับงาน
ที่ตัวเองทำได้** แต่ละเรื่องประกาศไว้ว่าเป็นของเมนูไหน/สิทธิ์ไหน แล้วระบบกรองให้เอง

| เรื่อง (ของจริงที่เพิ่งทำ)                          | คนที่ควรได้ยิน                |
| --------------------------------------------------- | ----------------------------- |
| ใบงานติดตั้งแยกตามวันติดตั้ง · ติดตั้งเพิ่มบนปฏิทิน | คนในโมดูล Book งาน + แดชบอร์ด |
| ตัวกรองประวัติสต็อก · พิมพ์ค้นหาสินค้าได้           | คนในโมดูลสต็อก                |
| เลขที่เช็คและวันที่หน้าเช็คในรายงานขายส่ง           | คนในโมดูลขายส่ง               |
| ชี้เมาส์ที่ไฟล์แนบแล้วเห็นไฟล์เลย                   | ทุกคนที่แนบไฟล์ได้            |

ถ้าไม่กรอง หัวหน้าช่างฟิล์มจะได้อ่านเรื่องคอลัมน์เช็คในรายงานขายส่งทุกครั้งที่อัปเดต
แล้วสัปดาห์ที่สามเขาจะเลิกอ่านทั้งหมด รวมถึงเรื่องที่เป็นของเขาจริง ๆ

## กติกาการเขียนเนื้อหา (ตัวที่ตัดสินว่าได้ผลหรือไม่)

ฟีเจอร์แบบนี้ไม่ค่อยตายเพราะโค้ด มันตายเพราะไม่มีใครเขียนเนื้อหาต่อหลังเดือนแรก

1. **เขียนพร้อมกับตอนแก้ ไม่ใช่เก็บไว้เขียนทีหลัง** — เหมือนที่ runbook ข้อ 16–22
   ถูกเขียนพร้อมกับงานแต่ละชิ้นอยู่แล้ว แปลงจาก runbook เป็นข้อความผู้ใช้ใช้เวลาสองนาที
   ส่วนการมานั่งเขียนย้อนหลังยี่สิบเรื่องทีเดียว คืองานที่ไม่มีใครทำ
2. **ภาษาร้าน ไม่ใช่ภาษาโปรแกรม** — "รายงานขายส่งบอกเลขที่เช็คแล้ว" ไม่ใช่
   "เพิ่มฟิลด์ chequeNo"
3. **เรื่องที่ไม่เปลี่ยนสิ่งที่ใครต้องทำ ไม่ต้องลง**
4. **หนึ่งรุ่นไม่เกิน 5 เรื่องบนแถบ** ที่เหลืออยู่ในหน้ารวม

## ทำงานอย่างไร (สำหรับการพัฒนา)

- **เนื้อหาอยู่ในโค้ด ไม่ใช่ในฐานข้อมูล** (`lib/releaseNotes.ts`) เพราะข้อความอธิบายโค้ด
  รุ่นนั้น มันจึงควรขึ้นและถอยไปพร้อมกับโค้ด ข้อความที่อยู่ในฐานข้อมูลจะประกาศฟีเจอร์
  ที่ยังไม่ได้ขึ้น หรือค้างอยู่หลังถอยรุ่นกลับ และต้องทำหน้าจอให้แก้ข้อความอีกหน้าหนึ่ง
- **สิ่งเดียวที่ต้องอยู่ในฐานข้อมูลคือ "ใครอ่านถึงไหนแล้ว"** — ตารางเล็ก ๆ
  `user_release_seen (user_id, last_seen, seen_at)` รายคน เพราะเครื่องหน้าร้านใช้ร่วมกัน
- **กรองด้วย `hasNav`/`caps` ที่มีอยู่แล้ว** ไม่ต้องมีรายชื่อบทบาทชุดใหม่ให้ลืมอัปเดต
- ป้าย "ใหม่" อ่านจากรายการเดียวกัน ไม่มีการเขียน "ใหม่" ฝังไว้ในหน้าจอตรง ๆ ที่จะ
  ค้างอยู่ตลอดไปเพราะไม่มีใครกลับมาลบ

  อ่านอะไรเลย ซึ่งใกล้เคียงความจริงมากกว่าการไม่เห็นอะไรเลย และเป็นปัญหาที่
  ข้อ 5 จะแก้ให้เองเมื่อมี "เริ่มใช้งาน"
- **ข่าวไม่มีวันหมดอายุ** รายการจะยาวขึ้นเรื่อย ๆ ตามรุ่น ถ้ายาวจนอ่านยาก ค่อย
  ตัดให้เหลือ 12 เดือนล่าสุด — ยังไม่ถึงตอนนั้น

### เรื่องพนักงานใหม่ (ข้อ 5) — ทำไมถึงไว้ทีหลัง

ที่ร้าน พนักงานใหม่มีคนสอนยืนอยู่ข้าง ๆ ทัวร์ในซอฟต์แวร์จึงมักกลายเป็นพิธีกรรมที่ทุกคน
กดข้าม สิ่งที่น่าจะได้ผลกว่าคือ **รายการงานสั้น ๆ ตามบทบาท** ("เปิดใบงานแรก · รับเงิน
ครั้งแรก · ปิดงาน") ที่ติ๊กแล้วหายไปเอง เพราะมันเรียงตามงานจริง ไม่ใช่ตามหน้าจอ —
แต่ควรทำหลังจากข้อ 1–4 เสร็จ และหลังระบบนิ่งกว่านี้

## ประกาศจากร้าน (ร้านบอกว่าสนใจ 23 พ.ย. 2569)

ตอนแรกเอกสารนี้เขียนว่า "ไม่ควรเอาไปปนกับมีอะไรใหม่" ซึ่งถูกครึ่งเดียว —
**ที่เก็บต้องแยก แต่ที่คนอ่านต้องเป็นที่เดียวกัน**

ถ้าประกาศของร้านมีกระดิ่งของตัวเอง แถบของตัวเอง และหน้าของตัวเอง พนักงานจะมี
สามที่ต้องคอยดู (กระดิ่ง + มีอะไรใหม่ + ประกาศ) แล้วจะมีที่หนึ่งที่ไม่มีใครดู
ในมุมของคนใช้ มันคือเรื่องเดียวกัน: "สิ่งที่ต้องรู้ แต่ยังไม่ใช่งานที่ต้องทำ"

**ที่เสนอ: ผิวหน้าเดียว สองแหล่ง**

|            | มีอะไรใหม่                   | ประกาศจากร้าน                            |
| ---------- | ---------------------------- | ---------------------------------------- |
| ใครเขียน   | คนที่แก้ระบบ                 | แอดมิน/ผู้บริหาร ผ่านหน้าจอในระบบ        |
| เก็บที่ไหน | ในโค้ด ขึ้นและถอยไปพร้อมโค้ด | ฐานข้อมูล แก้ได้ทันทีไม่ต้องขึ้นระบบใหม่ |
| อายุ       | อยู่ถาวร เป็นประวัติ         | มีวันเริ่ม–วันหมดอายุ แล้วหายไปเอง       |
| ลำดับ      | เรียงตามรุ่น                 | **ปักไว้บนสุด** ระหว่างที่ยังไม่หมดอายุ  |
| ใครเห็น    | ตามสิทธิ์รายเมนู             | เลือกได้: ทุกคน / เฉพาะสาขา / เฉพาะบทบาท |

วันหมดอายุคือข้อที่ต่างกันจริง ๆ และเป็นเหตุผลที่ต้องเก็บคนละที่: ประกาศว่า
"1 ธ.ค. ปิดปรับปรุงระบบ" ไม่มีประโยชน์อีกเลยหลังวันที่ 1 ธ.ค. และประกาศเก่าที่
ค้างอยู่บนจอ คือเหตุผลที่คนเลิกอ่านประกาศ ส่วนข่าวการเปลี่ยนแปลงเป็นประวัติที่
มีค่าตลอด

**สิ่งที่ต้องทำเพิ่ม** — ตารางเก็บประกาศ, หน้าจอให้แอดมินพิมพ์ (หัวข้อ เนื้อหา
ช่วงวันที่ ใครเห็น ด่วนหรือไม่), และขยายตารางจำการอ่านให้จำรายเรื่องได้ ไม่ใช่
แค่รายรุ่น ประมาณงานเท่ากับข้อ 1–2 ที่ทำไปแล้ว

**ต้องถามก่อนเริ่ม:** ใครมีสิทธิ์ประกาศได้บ้าง (แอดมินอย่างเดียว หรือผู้บริหาร
ด้วย) และประกาศด่วนควรเด้งแรงกว่าแถบปกติไหม — ถ้าปิดระบบพรุ่งนี้เช้า แถบบาง ๆ
ที่กดปิดได้ อาจเบาเกินไป

## ต้องให้ร้านตัดสินใจ

1. **ทำอะไรก่อน** — "มีอะไรใหม่" (แนะนำ) หรือ "เริ่มใช้งาน" สำหรับพนักงานใหม่
2. **ใครเขียนข้อความภาษาไทย** — เขียนไปพร้อมกับแต่ละการแก้ (แนะนำ) หรือร้านเขียนเองทีหลัง
3. **กด "ไว้ก่อน" แล้วหายเลย + เหลือจุดสีจนกว่าจะอ่าน** (แนะนำ) หรือให้กลับมาเตือนพรุ่งนี้
   เหมือนกระดิ่ง
4. **ประกาศจากร้าน** — ร้านบอกว่าสนใจ (23 พ.ย. 2569) ดูหัวข้อถัดไป
5. **อยากรู้ไหมว่าใครอ่านแล้วบ้าง** — มีประโยชน์เฉพาะกับเรื่องประเภท "ความหมายเปลี่ยน"
   ที่ถ้าไม่รู้แล้วจะอ่านตัวเลขผิด ถ้าอยากได้ ต้องเก็บเพิ่มรายเรื่อง ไม่ใช่แค่รายรุ่น
6. **ย้อนหลังแค่ไหน** — รุ่นแรกควรรวม 22 เรื่องที่ทำไปแล้วทั้งหมด หรือเริ่มนับจากรุ่นถัดไป
